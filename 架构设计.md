### 1.3 设计要点

- **功能权限与数据范围物理隔离**：两套表，通过 `role_id` 关联，但互不耦合。
- **角色层级继承**：`role.parent_role_id` 自引用，查询权限时递归获取父角色权限。
- **审批流配置化**：`approval_flow_config` 表驱动状态转移，新增节点只需加配置行。
- **字段可见性按阶段配置**：与角色解耦，同一个角色在不同审批阶段看到不同字段。

### 2.2 功能权限解析

```java
@Service
public class FunctionPermissionResolver {

    /**
     * 获取用户所有有效权限码（含角色继承 + 多角色并集）
     */
    public Set<String> getUserPermissions(Long userId) {
        // 1. 查用户所有角色
        List<Role> roles = getUserRoles(userId);

        // 2. 递归展开角色层级（父角色权限自动继承）
        Set<Long> allRoleIds = expandRoleHierarchy(roles);

        // 3. 查所有角色-权限关联
        List<Permission> permissions = rolePermissionMapper
            .selectByRoleIds(allRoleIds);

        // 4. 返回权限码集合
        return permissions.stream()
            .map(Permission::getCode)
            .collect(Collectors.toSet());
    }

    public boolean hasPermission(Long userId, String permissionCode) {
        Set<String> permissions = getUserPermissions(userId);
        return permissions.contains(permissionCode);
    }
}
```

### 2.3 数据范围解析

```java
@Service
public class DataScopeResolver {

    /**
     * 解析用户的数据范围，返回 SQL 条件片段
     * 多角色取并集（OR 拼接）
     */
    public DataScopeResult resolveScope(Long userId) {
        List<Role> roles = getUserRoles(userId);
        List<String> conditions = new ArrayList<>();
        Set<Long> allDeptIds = new HashSet<>();

        for (Role role : roles) {
            RoleDataScope scope = roleDataScopeMapper.selectByRoleId(role.getId());
            switch (scope.getScopeType()) {
                case SCOPE_SELF:
                    // contract.applicant_id = #{currentUserId}
                    conditions.add("c.applicant_id = " + userId);
                    break;
                case SCOPE_DEPT:
                    // c.dept_id IN (用户主部门及兼任部门)
                    Set<Long> userDeptIds = getUserDeptIds(userId);
                    conditions.add("c.dept_id IN (" + joinIds(userDeptIds) + ")");
                    break;
                case SCOPE_CUSTOM:
                    // c.dept_id IN (角色配置的自定义部门)
                    List<Long> customDeptIds = scopeDeptMapper
                        .selectDeptIdsByScopeId(scope.getId());
                    conditions.add("c.dept_id IN (" + joinIds(customDeptIds) + ")");
                    break;
                case SCOPE_ALL:
                    // 无限制，但为了并集统一，返回 1=1
                    conditions.add("1=1");
                    break;
            }
        }

        // 多角色取并集：OR 拼接
        String sqlCondition = conditions.isEmpty()
            ? "1=0"  // 无角色时 deny-all
            : "(" + String.join(" OR ", conditions) + ")";

        return new DataScopeResult(sqlCondition);
    }
}
```

## 3. 功能权限与数据范围：独立建模 + 决策求交

### 3.1 为什么必须独立建模

| 混在一起 | 独立建模 |
|----------|----------|
| 每个"功能+范围"组合需要一个角色 | 角色只关心功能，数据范围独立配置 |
| N 种功能 × M 种范围 = N×M 个角色 | N 个角色 + M 种范围配置 |
| 修改范围影响角色定义 | 修改范围只改 `role_data_scope` 一行 |
| 无法表达"看全部、改自己" | 通过 per-(角色, 操作) 矩阵实现 |

**具体例子**：假设有一个"审计员"角色，需要 `contract:view` 权限 + 全部数据范围 + `contract:delete` 权限 + 仅本人数据范围。如果混在一起，需要两个角色："审计员-全部"和"审计员-本人"。独立建模只需要一个角色 + 按操作配置范围。

### 3.2 决策时求交的流程

```
用户请求 "查看合同列表"

步骤1: 功能权限检查
  hasPermission(userId, "contract:view") → true/false
  false → 直接返回 403

步骤2: 数据范围解析
  resolveScope(userId) → SQL WHERE 条件片段
  例如: "(c.applicant_id = 1 OR c.dept_id IN (1,3))"

步骤3: 求交执行
  SELECT * FROM contract c
  WHERE (c.applicant_id = 1 OR c.dept_id IN (1,3))  ← 数据范围
  [AND 其他业务条件]
  [ORDER BY ... LIMIT ...]

步骤4: 字段级过滤（后处理）
  根据合同当前状态，对结果集逐行应用字段可见性配置
```

### 3.3 求交的关键代码

```java
@Service
public class ContractService {

    public IPage<ContractVO> listContracts(Long userId, PageQuery query) {
        // 第1步：功能权限
        if (!functionPermissionResolver.hasPermission(userId, "contract:view")) {
            throw new AccessDeniedException("无查看合同权限");
        }

        // 第2步：获取数据范围 SQL 条件
        DataScopeResult scope = dataScopeResolver.resolveScope(userId);

        // 第3步：执行查询（数据范围作为 SQL 条件注入）
        Page<Contract> page = contractMapper.selectPageWithScope(
            new Page<>(query.getPage(), query.getSize()),
            scope.getSqlCondition(),   // ← 参数化注入，非 ${} 拼接
            query
        );

        // 第4步：字段级过滤
        return page.convert(contract -> toVO(contract));
    }
}
```

### 3.4 MyBatis-Plus 数据范围拦截器

```java
@Component
public class DataScopeInterceptor implements InnerInterceptor {

    @Override
    public void beforeQuery(Executor executor, MappedStatement ms,
                            Object parameter, RowBounds rowBounds,
                            ResultHandler resultHandler, BoundSql boundSql) {
        // 从 ThreadLocal 获取当前用户的数据范围条件
        DataScopeResult scope = DataScopeContextHolder.get();
        if (scope != null && scope.hasCondition()) {
            // 改写原始 SQL，注入数据范围条件
            String originalSql = boundSql.getSql();
            String scopedSql = injectScopeCondition(originalSql, scope.getSqlCondition());
            // 通过反射替换 boundSql 中的 SQL
            setBoundSql(boundSql, scopedSql);
        }
    }

    private String injectScopeCondition(String originalSql, String condition) {
        // 在 WHERE 子句后追加条件
        // 原始: SELECT * FROM contract c WHERE c.status = ?
        // 改写: SELECT * FROM contract c WHERE c.status = ? AND (c.applicant_id = ? OR c.dept_id IN (...))
        return originalSql.replace("WHERE", "WHERE " + condition + " AND ");
    }
}
```

### 3.5 per-(角色, 操作) 范围矩阵（加分项）

```sql
-- 扩展：按操作粒度配置数据范围
CREATE TABLE role_permission_scope (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    role_id BIGINT NOT NULL,
    permission_code VARCHAR(64) NOT NULL,     -- 具体操作: contract:view, contract:edit
    scope_type VARCHAR(16) NOT NULL,          -- 该操作对应的数据范围
    UNIQUE (role_id, permission_code)
);
```

这样就能实现"看全部、改自己"——同一角色，`contract:view` 配 `SCOPE_ALL`，`contract:edit` 配 `SCOPE_SELF`。

## 4. 审批流状态机与节点权限门控

### 4.1 状态机设计

```
                  ┌─────────┐
                  │  DRAFT  │  (草稿)
                  └────┬────┘
                       │ submit (U1: contract:create)
                       ▼
              ┌────────────────┐
              │ PENDING_ADMIN  │  (待合同管理员处理)
              └───────┬────────┘
                      │ process (U2: contract:process)
                      ▼
              ┌──────────────────┐
              │ PENDING_MANAGER  │  (待部门经理审批)
              └───────┬──────────┘
                      │ approve (U3: contract:approve)
                      ▼
              ┌─────────────────┐
              │ PENDING_LEADER  │  (待领导审批)
              └───────┬─────────┘
                      │ approve (U4: contract:approve)
                      ▼
              ┌──────────────┐
              │  APPROVED    │  (已通过，终态)
              └──────────────┘

    从 DRAFT 可 withdraw (U1) → WITHDRAWN (终态)
    从任何非终态可 delete (U4: contract:delete) → DELETED (终态)
```

### 4.2 节点门控（双重门控）

每个节点操作需要同时满足两个条件，缺一不可：

```
节点操作通过 = 功能权限门控 ∧ 状态机门控

功能权限门控: hasPermission(user, "contract:approve")
状态机门控:   contract.status == PENDING_MANAGER && flowConfig.allowTransition(PENDING_MANAGER, "approve")
```

**门控实现**：

```java
@Service
public class ApprovalFlowService {

    public void approve(Long userId, Long contractId) {
        // 门控1: 功能权限（由 @PreAuthorize 或显式调用）
        // 已由 Spring Security 拦截

        // 门控2: 状态机门控
        Contract contract = contractMapper.selectById(contractId);
        ApprovalFlowConfig config = flowConfigMapper
            .selectByFromStatusAndAction(contract.getStatus(), "APPROVE");

        if (config == null) {
            // 当前状态不允许此操作 → 节点顺序违规
            throw new BusinessException("当前合同不在可审批状态，当前状态: "
                + contract.getStatus());
        }

        // 门控3: 数据范围（如果合同不在用户范围内，SQL 层查不到）
        // 前面查询时已施加数据范围

        // 执行状态转移
        contract.setStatus(config.getToStatus());
        contractMapper.updateById(contract);

        // 记录审批记录
        saveApprovalRecord(contractId, config.getFromStatus(),
            config.getToStatus(), "APPROVE", userId);

        // 记录审计日志
        auditLogService.log(userId, "APPROVE", "CONTRACT",
            contractId, "SUCCESS", "审批通过");
    }
}
```

```sql
('PENDING_LEADER',  'DELETED',          'DELETE',   'contract:delete',  'LEADER',         8);
```

### 4.4 节点顺序强制

节点顺序通过**状态机转移规则**强制，而非代码中的 if-else：

1. 每个操作只能从特定的 `from_status` 执行。
2. `U3` 尝试审批状态为 `PENDING_ADMIN` 的合同时，`flowConfigMapper.selectByFromStatusAndAction("PENDING_ADMIN", "APPROVE")` 返回 null → 抛出异常。
3. 新增审批节点只需在配置表中加一行，无需改代码。

#### 字段可见性过滤

```java
@Component
public class FieldVisibilityFilter {

    /**
     * 根据合同状态 + 字段配置，过滤/脱敏 VO 字段
     */
    public ContractVO filter(Contract contract) {
        ContractVO vo = BeanUtils.copyProperties(contract, ContractVO.class);
        List<FieldVisibilityConfig> configs = fieldConfigService
            .getByStage(contract.getStatus().name());

        for (FieldVisibilityConfig cfg : configs) {
            switch (cfg.getVisibility()) {
                case HIDDEN:
                    // 设为 null，Jackson @JsonInclude(NON_NULL) 自动隐藏
                    BeanUtils.setProperty(vo, cfg.getFieldName(), null);
                    break;
                case MASKED:
                    String original = BeanUtils.getProperty(vo, cfg.getFieldName());
                    BeanUtils.setProperty(vo, cfg.getFieldName(), mask(original));
                    break;
                case VISIBLE:
                default:
                    // 不处理
                    break;
            }
        }
        return vo;
    }

    private String mask(String value) {
        if (value == null || value.length() <= 4) return "****";
        return value.substring(0, 2) + "****" + value.substring(value.length() - 2);
    }
}
```

## 6. 备选方案与取舍

### 6.1 方案一：Spring Security + MyBatis-Plus 拦截器（推荐方案）

**即本文档描述的方案**。

**优点**：
- 与 Spring 生态深度集成，无需引入额外依赖。
- MyBatis-Plus 的 `InnerInterceptor` 机制天然适合 SQL 改写。
- Spring Security 的 `@PreAuthorize` 方法级鉴权成熟稳定。
- 学习成本低，团队成员容易上手。
- 对于单租户 OA 系统，功能完全足够。

**缺点**：
- 数据范围条件以字符串拼接方式注入 SQL，需要确保参数化防注入。
- 策略规则在代码中（注解 + 数据库配置），修改需要重新部署（但配置表可热更新）。
- 不支持复杂的策略表达式（如"A 且 B 且 (C 或 D)"），但本需求不需要。

### 6.2 方案二：Casbin 策略引擎

**思路**：引入 Casbin 作为独立的策略决策点（PDP），将 RBAC 模型和策略写入 `.conf` 文件。

```
[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act

[role_definition]
g = _, _

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = g(r.sub, p.sub) && keyMatch(r.obj, p.obj) && keyMatch(r.act, p.act)
```

**优点**：
- 策略外部化，修改策略无需重启应用。
- 支持 RBAC + ABAC 混合模型。
- 有完善的策略管理 API 和可视化工具。
- 多语言支持，前后端可用同一套策略定义。

**缺点**：
- 引入额外依赖和学习成本。
- **数据范围过滤不是 Casbin 的强项**：Casbin 擅长"能不能做"的判断，但"对哪些行做"需要额外实现。需要自己在 Adapter 中实现数据范围 SQL 生成。
- 对于本需求（单租户、4 个角色、10 个权限码），引入 Casbin 是**过度工程**。
- 策略文件的管理和维护需要额外的基础设施。

**结论**：**不推荐当前阶段使用 Casbin**。但保留升级路径——当满足以下条件时应升级：
- 角色和权限码数量超过 20 个且频繁变更。
- 需要跨服务共享策略（微服务架构）。
- 需要支持复杂的策略表达式（如带条件的 ABAC 规则）。
- 需要策略版本管理和审计。

### 6.3 方案三：OPA (Open Policy Agent)

**思路**：使用 OPA 作为独立 sidecar，通过 Rego 语言编写策略。

```rego
package contract.auth

default allow = false

allow {
    input.user.roles[_] == "LEADER"
    input.action == "approve"
    input.contract.status == "PENDING_LEADER"
}
```

**优点**：
- 策略即代码，支持极其复杂的逻辑。
- 独立进程，与业务代码完全解耦。
- 有丰富的工具链（OPA Gateway、Bundle 管理、决策日志）。
- 适合大型分布式系统。

**缺点**：
- **为单租户 OA 上 OPA 是严重过度工程**。
- 需要部署和维护额外的 OPA 服务（或 sidecar）。
- Rego 语言学习曲线陡峭。
- 每次鉴权都需要一次 HTTP 调用（或内嵌 OPA 增加内存开销）。
- 数据范围过滤同样不是 OPA 的强项，需要额外实现。

**结论**：**不推荐**。OPA 适用于微服务网格、Kubernetes 准入控制、API Gateway 策略等场景，本需求完全不需要。

### 6.4 方案四：Zanzibar（Google 式 ReBAC）

**思路**：使用关系元组（`user → relation → object`）建模权限，如 `user:U1 → viewer → contract:123`。

**优点**：
- 天然支持对象级权限（谁对哪个文档有什么权限）。
- 支持关系链传递（如 `folder → document` 的继承）。
- Google Zanzibar 是 Google Docs/YouTube 的权限系统，经过超大规模验证。

**缺点**：
- **需要独立的图数据库或 Zanzibar 实现**（如 SpiceDB）。
- 本需求中，数据范围已经是行级过滤，不需要对象级关系链。
- 本需求没有"文档→文件夹→空间"的嵌套归属关系，Zanzibar 的优势发挥不出来。
- 运维复杂度极高。

**结论**：**不推荐**。如果未来出现"合同归属项目→项目归属部门→部门归属事业部"的多层嵌套关系，可以考虑引入 ReBAC 思维，但用递归 SQL 实现，而非上 Zanzibar。

### 6.5 为什么不用硬编码 if-else

硬编码 if-else 的反模式：

```java
// 反模式示例
if (user.getRoleName().equals("LEADER")) {
    // 领导能看到全部
    queryWrapper.eq("dept_id", user.getDeptId());
} else if (user.getRoleName().equals("DEPT_MANAGER")) {
    // 部门经理只能看本部门
    queryWrapper.eq("dept_id", user.getDeptId());
} else if (user.getRoleName().equals("APPLICANT")) {
    // 申请人只看自己
    queryWrapper.eq("applicant_id", user.getId());
}
```

**问题**：
1. **新增角色要改代码**：每次新增角色都要加 if 分支。
2. **对角色名字符串脆弱**：角色名变更导致逻辑失效。
3. **无法测试**：每个分支需要 mock 不同角色。
4. **无法复用**：每个接口都要写一遍相同的 if-else。
5. **违反开闭原则**：对修改不封闭。

**正确做法**：策略即配置，代码只做策略执行。

### 6.6 数据范围施加到查询的两种方式对比

| 方式 | 实现 | 优点 | 缺点 |
|------|------|------|------|
| **应用层过滤** | 查出全部数据，Java 内存中过滤 | 简单 | 性能差，无法分页 |
| **SQL 改写** | 拦截 SQL，注入 WHERE 条件 | 性能好，支持分页 | 实现复杂，需防 SQL 注入 |

**选择 SQL 改写**，具体实现：

```java
// MyBatis-Plus DataScopeInterceptor
// 在 SQL 执行前改写 SQL
// 原始: SELECT * FROM contract c WHERE c.status = 'PENDING_MANAGER'
// 改写: SELECT * FROM contract c WHERE (c.applicant_id = ? OR c.dept_id IN (?)) AND c.status = 'PENDING_MANAGER'

// 使用参数化查询，所有用户输入通过 PreparedStatement 传参
// 不使用 ${} 字符串拼接
```

### 6.7 方案对比总结

| 维度 | 方案一（推荐） | 方案二（Casbin） | 方案三（OPA） | 方案四（Zanzibar） |
|------|--------------|-----------------|--------------|-------------------|
| 复杂度 | 低 | 中 | 高 | 极高 |
| 功能权限 | 注解 + 数据库 | 策略文件 | Rego 策略 | 关系元组 |
| 数据范围 | SQL 改写 | 需额外实现 | 需额外实现 | 需额外实现 |
| 策略外部化 | 部分（配置表） | 完全 | 完全 | 完全 |
| 适合场景 | 单租户 OA | 中型 SaaS | 大型分布式 | 超大规模文档系统 |
| 本项目推荐 | **是** | 升级路径 | 否 | 否 |

### 7.1 角色继承查询

```sql
-- 递归查询角色及其所有父角色的权限
WITH RECURSIVE role_hierarchy AS (
    SELECT id, parent_role_id FROM role WHERE id = #{roleId}
    UNION ALL
    SELECT r.id, r.parent_role_id
    FROM role r
    INNER JOIN role_hierarchy rh ON r.id = rh.parent_role_id
)
SELECT DISTINCT p.code
FROM role_hierarchy rh
JOIN role_permission rp ON rp.role_id = rh.id
JOIN permission p ON p.id = rp.permission_id;
```
